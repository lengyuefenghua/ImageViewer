# 调试修复

硬 bug 的诊断纪律。跳过阶段必须有明确理由。

探索代码库时，先读与问题相关的项目指令和 ADR（如有），建立相关模块的清晰心智模型。

核心规则：

```text
没有根因调查，不得修复
没有会红的反馈环，不得猜假设
```

环造出来之前，禁止读代码猜原因搭理论；为造环而读（找入口、seam、复现步骤）是允许的。

## 保密处理

展示命令、输出和捕获的产物前，**先打码每一个秘密**——用 `<REDACTED>` 占位。环对着环境变量构建，凭据留在环境里而不是展示出来。捕获的产物带 auth 头：只引用有信号的几行。

打码后仍不够诊断时，说明并问用户。

## 阶段 1 — 先造反馈环（核心）

**造环是最关键的一步。** 其余都是机械动作。只要有一个**紧**的通过/失败信号——能在**这个** bug 上变红的——你就能找到原因；二分、假设检验、插桩都只是消费它。没有它，盯多久代码都没用。

在这里投入不成比例的努力。**激进、有创意、拒绝放弃。**

构建方式，按此顺序尝试：

1. **失败测试**，在能触达 bug 的任意 seam——单测、集成、e2e。
2. **Curl / HTTP 脚本**，对着跑着的 dev server。
3. **CLI 调用**，喂 fixture 输入，stdout 与已知好的快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace**：把真实网络请求/负载/事件日志存盘，隔离重放进代码路径。
6. **一次性 harness**：拉起系统的最小子集（一个服务、mock 依赖），用一次函数调用走通 bug 路径。
7. **属性/模糊环**：bug 是"有时输出错"，就跑 1000 个随机输入找失败模式。
8. **二分 harness**：bug 出现在两个已知状态（commit、数据集、版本）之间，就把"在状态 X 启动、检查、重复"自动化，以便 `git bisect run`。
9. **差分环**：同一输入跑旧版本 vs 新版本（或两套配置），diff 输出。
10. **HITL 驱动**：最后手段。必须人工点击时，把环的每一步写成结构化提问——给用户确切的操作指令和要反馈的输出，让环仍然结构化。捕获输出喂回给你。

把反馈环造对，bug 就解决了 90%。

### 收紧环

把环当产品对待。有了环之后，**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 信号能更锐吗？（断言具体症状，而不是"没崩"。）
- 能更确定吗？（钉住时间、seed RNG、隔离文件系统、冻结网络。）

30 秒的 flaky 环比没有环好不了多少；2 秒的确定性环是紧的——调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发跑 100 遍、并行化、加压、收窄时间窗、注入 sleep。50% 的 flaky bug 可调试；1% 不行——一直把复现率提到可调试为止。

### 实在造不出环

停下并明说。列出你试了什么。向用户要：(a) 能复现的环境的访问权，(b) 打码后的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**没有环，不得进入假设阶段。**

### 完成标准 — 一个会红的紧环

阶段 1 完成 = 环**紧**且**能红**，四条件全满足才能进下一阶段：

- [ ] **能红** — 驱动真实 bug 代码路径，断言**用户的确切症状**，能在本 bug 上变红、修好后变绿。不是"跑起来没报错"——必须能**抓住这个具体 bug**。
- [ ] **确定** — 每次运行同一个结论（flaky bug：按上文钉住的高复现率）。
- [ ] **快** — 秒级，不是分钟级。
- [ ] **可无人运行** — 你能无人值守地跑；人工介入只通过结构化提问（见上）驱动用户。

发现自己没这条命令就开始读代码搭理论——**停，直接跳假设正是要避免的失败。** 没有能红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

跑环，看它变红——bug 出现。

确认：

- [ ] 环产生的是**用户**描述的失败模式——不是碰巧在附近的另一个失败。错 bug = 错修。
- [ ] 多次运行可复现（或非确定性 bug 达到足够高的复现率）。
- [ ] 捕获了确切症状（错误消息、错误输出、慢的耗时），后续阶段据此验证修复。

### 最小化

红了之后，把复现缩到**仍会红的最小场景**。一次砍一个输入、调用方、配置、数据、步骤，每砍一步重跑环——只留对失败有承重作用的部分。

最小复现缩小阶段 4 的假设空间（可怀疑的动件更少），并作为阶段 5 的干净回归测试。

完成标准：**每个剩余元素都承重**——去掉任何一个环都会变绿。

不复现**且**不最小化，不得继续。

## 阶段 3 — 根因调查 + 模式分析

环已经红了，**现在**才允许读代码建理解：

1. 读完整错误、堆栈、日志、命令输出和行号。
2. 检查最近改动和相关配置/环境。
3. 从症状向上回溯数据/控制流到源头。
4. Grep 你要改的函数/模块的所有调用方；根因修法（共享逻辑里一道防护）比调用方到处加防护更小。
5. 在仓库里找相似的可工作代码，对比坏路径与好路径，列出具体差异和假设。

## 阶段 4 — 假设

先产出 **3-5 个排好序的假设**，再测任何一个。单假设生成会锚定在第一个像样的想法上。

每个假设必须**可证伪**：说出它的预测。

> 格式一："如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。"
> 格式二："我认为 <根因>，因为 <证据>。"

说不出预测，假设就是感觉——丢弃或磨尖它。

**测试前把排序列表给用户看。** 他们常有能立刻重排的领域知识（"我们刚部署了 #3 的改动"），或知道已经排除过的假设。便宜检查点，省大量时间。不要阻塞——用户不在就按你的排序继续。

## 阶段 5 — 单变量探查 + 修复

### 探查

每个探针必须对应阶段 4 的具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，环境支持就用。一个断点胜过十行日志。
2. **定向日志**，打在能区分假设的边界上。
3. 永远不要"全量打日志再 grep"。

**每条调试日志打唯一前缀标签**，如 `[DEBUG-a4f2]`。收尾时一次 grep 清干净。没标签的日志活下来；有标签的日志死掉。

**性能分支。** 性能回归时日志通常不对。改：先立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测后修。

### 修复

回归测试**先于修复**写——但只在存在**正确 seam** 时。

正确 seam 是测试能锻炼**真实 bug 模式**、如同它在调用现场发生的那样。唯一可用的 seam 太浅时（bug 需要多个调用方而测试只有一个调用方、单测复刻不出触发 bug 的链条），在那里的回归测试给出虚假信心。

**没有正确 seam 存在时，这本身就是发现。** 记下来。代码库架构在阻止这个 bug 被锁死。标记给下一阶段。

存在正确 seam 时：

1. 把最小化复现转成该 seam 上的失败测试。
2. 看着它失败。
3. 用最小安全改动修根因。
4. 看着它通过。
5. 用原始（未最小化）场景重跑阶段 1 的反馈环。

连续三次修复尝试失败，停下来质疑架构或假设，再试下一个补丁。

## 阶段 6 — 清理 + 复盘

声明完成前必须：

- [ ] 原始复现不再复现（重跑阶段 1 的环）
- [ ] 回归测试通过（或 seam 缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 正确的假设写进 commit / PR 消息——让下个调试者受益

**最后问：什么本可预防此 bug？** 答案涉及架构变更时（没有好的测试 seam、缠结的调用方、隐藏耦合），**修复落地后**向用户提出改进建议——现在你比开始时信息更多。
