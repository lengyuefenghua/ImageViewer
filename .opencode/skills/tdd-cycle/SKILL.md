# TDD 循环

核心规则：

```text
默认不写测试
只有「不写会导致灾难、且该灾难可稳定复现」的行为才写；入选的走 RED-GREEN
```

没有亲眼看到测试失败，就无法确认测试真的在检查预期行为。

TDD 是红 → 绿循环，但只有通过准入闸的行为才进入循环。每个循环都按本技能检查：好测试、seams、反模式、循环规则——循环前和循环中都要查，不要循环后才查。

探索代码库时，先读与触碰区域相关的项目指令和 ADR（如有）。

## 准入闸：漏测后果

写任何测试之前，先回答：**如果这个行为悄悄坏了、又没有这个测试，会发生什么？**

逐条对照后果维度：

| 维度 | 具体表现 |
| --- | --- |
| 崩溃 / 闪退 | 未捕获异常、空引用、越界、断言失败、进程/线程退出、界面白屏、启动失败 |
| 内存 / 资源泄漏 | 句柄·文件·socket·连接·锁未释放；监听器·定时器·线程累积；缓存/队列无界增长 |
| 系统资源异常占用 | 死循环、死锁、无界 CPU/内存/磁盘增长、连接池耗尽、请求永久挂起 |
| 数据损坏 / 丢失 | 写坏、半写、并发覆盖、迁移丢字段或重复、静默截断、不可逆副作用 |
| 破坏系统运行 / 级联 | 启动即崩、破坏共享状态或契约、连带其他功能、鉴权/安全绕过 |
| 静默错误结果 | 不崩但结果错且难察觉：算错金额、判错权限、迁移结果错 |

写测试必须**同时**满足：

1. 命中上面至少一个后果维度。
2. 能指出**具体触发场景**。
3. 该测试能**稳定复现**这个后果。
4. 没有更便宜的检查（类型、lint、启动冒烟、一行断言）能挡住。

缺任意一条就**不写**，在任务或记录里写一句 `无测试：<原因>`。

因为不设数量上限，这道闸是唯一的量控制：答不出后果就没资格写测试。测试任务里记下 `后果：<维度>（触发：<场景>）`。

## 默认不写

不追求覆盖率；以下默认不写（除非用户点名）：

- 接线、依赖注入、纯转发、getter/setter。
- 简单 CRUD 与框架已保证的行为。
- 配置值、常量、样式、文案、布局。
- 「每个函数/分支/导出各来一个」。
- 低风险边角、一次性脚本与原型。
- 界面外观（改用 `ui-visual-verify` 的真实截图验证）。

一个测试只对应一个后果；同一后果已有测试覆盖就不重复写。

**不要文字断言**：不断言具体文案、提示词、日志等文本内容；断言核心行为与状态——返回值、状态转换、调用效果、数量/结构（见反模式）。

## 什么是好测试

测试通过**公共接口**验证行为，不验证实现细节。代码可以整个换掉，测试不该动。好测试读起来像规格说明——"有效购物车可以结算"直接告诉你存在什么能力——并且能扛过重构，因为它不关心内部结构。

## Seams — 测试写在哪

**seam** 是你在其上测试的公共边界：不用伸进内部就能观察行为的接口。测试活在 seam 上，永远不打内部。

**只在预定的 seam 上测试。** 写任何测试之前，先写下被测的 seams 并与用户确认。不在未确认的 seam 上写测试。不可能什么都测——事先约定 seams，测试火力才能落在关键路径和复杂逻辑上，而不是每个边角。

先问："公共接口是什么，测哪些 seams？"

## 反模式

- **实现耦合** — mock 内部协作者、测私有方法、或通过旁路验证（查数据库而不是用接口）。特征：重构后测试崩了但行为没变。
- **同义反复** — 断言用代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`），按构造必然通过，永远不可能和代码不一致。期望值必须来自独立真源——已知好的字面量、手算例子、规格。
- **横向切片** — 先写完全部测试，再写完全部实现。批量测试验证的是**想象中**的行为：你测的是事物的形状而不是用户可见行为，测试对真实变化失敏，且在理解实现之前就锁死了测试结构。改用**垂直切片**——一个测试 → 一个实现 → 重复，每个测试是一颗**曳光弹**，回应上一循环教给你的东西。
- **文字断言** — 断言具体文案、提示词、日志等文本内容（`msg === "需要确认：bash"`、`prompt.includes("lean-check")`、`assert.match(output, /已保存/)`）。文本随措辞变化而碎，且测的不是核心行为。改为断言行为与状态：返回值、状态转换、调用效果、数量/结构。
- **凑数测试** — 说不出致命后果、或该后果不可复现却仍写下的测试。特征：删掉它没人会发现；只为「看起来覆盖了」而存在。

## Mock 边界

只在**系统边界** mock：

- 外部 API（支付、邮件等）
- 数据库（有时——优先测试库）
- 时间/随机性
- 文件系统（有时）

不要 mock：

- 自己的类/模块
- 内部协作者
- 任何你控制的东西

系统边界处设计易 mock 的接口：依赖注入传入外部依赖；SDK 风格接口（每个外部操作一个具体函数）优于通用 fetcher（mock 无需条件逻辑）。

## 循环规则

1. **红先于绿**：先写失败测试，再写只够通过的代码。不预测未来测试，不加投机功能。
2. **一次一片**：每个循环一个 seam、一个测试、一个最小实现。
3. **REFACTOR 不属于循环**：归审查阶段（见 `review-change`），不属于红绿实现循环。

## 循环步骤

1. RED：为一个通过准入闸的行为写最小测试。
2. 运行聚焦测试。
3. 确认它因预期原因失败，而不是拼写或 setup 错误。
4. GREEN：写让测试通过的最小生产代码。
5. 运行同一个聚焦测试并确认通过。
6. 运行相邻或全部相关验证。
7. 仅在测试保持绿色的前提下 REFACTOR。

## 如果先写了实现

不要叫它 TDD。二选一：

- 删掉实现，重做测试先行；或
- 明确报告这是先实现后补测试的证据，可信度较低。

不要一边保留实现当参照，一边假装测试驱动了它。

## 好测试规则

- 一个测试一个行为。
- 名字描述行为（WHAT 不是 HOW）。
- 优先真实代码而非 mock，除非外部边界使 mock 必要。
- 测可观察行为，不测实现细节。
- 只对通过准入闸的行为写测试；断言行为与状态（返回值、状态转换、调用效果、数量/结构），不做文字断言（文案、提示词、日志文本）。
- 回归测试必须在旧行为上失败、在修复后通过。
