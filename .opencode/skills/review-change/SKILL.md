# 审查变更

## 审查级别

- **full**：双轴完整审查（本技能正文），复杂 diff 可派并行只读子代理。
- **patch**：轻量审查，主控直接执行；不派子代理、不逐条跑 12 条坏味道基线、不写双轴报告。
- **tiny**：不审查。

### patch 轻量审查清单

1. **需求符合**：改动正好覆盖需求，无范围蔓延。
2. **最小性**：无无关改动、顺手清理。
3. **日志与注释**：关键路径日志点、关键注释已具备（对照 AGENTS.md）。
4. **验证证据**：聚焦命令已运行且输出已读。

输出 3-5 行简短结论；发现 Critical/Important 问题按 full 标准处理。

## 双轴审查（仅 full）

双轴审查，**两轴刻意分开汇报，禁止合并重排**——一轴过不代表另一轴过：

- **Spec 轴** — 代码是否忠实实现了规格要求？TDD 证据是否成立？
- **Standards 轴** — 代码是否遵守仓库标准和代码质量基线？

发现按严重程度分级：Critical / Important / Suggestion。存在未解决的重要问题时不得通过。

## Spec 轴

1. **规格符合性**：恰好实现了 requirement，不多不少。漏实现 = Critical；范围蔓延（spec 没要求的行为）= Critical。
2. **TDD 证据**：RED 和 GREEN 步骤由最近的命令输出或任务记录证明；RED 因预期原因失败，不是拼写/setup 错误。
3. **界面视觉证据**（界面变更）：是否有改动后的**真实截图**且已观察、与 spec 视觉要求一致；缺失或未观察 = Important。

## Standards 轴

3. **代码质量**：简单、清晰、局部化，没有不必要的抽象。逐条比对坏味道基线（见下）。
4. **Lean 精简**：有没有能删、能复用、能用标准库/原生替换、能写得更小的东西？
5. **术语一致性**：命名是否使用 `CONTEXT.md` 的词汇；引入的新领域概念是否已回写。
6. **风险检查**：输入校验、数据丢失、安全、隐私、无障碍、迁移、回滚。
7. **文风检查**：
   - 推理痕迹残留（步骤叙述、测试走查、被拒方案复盘）
   - 变更史叙事（"之前/现在/不再"）——只允许在 ADR 和归档中
   - 强调滥用（加粗/大写泛滥，什么都不突出）
   - 同一规则多处重复——one home per fact，留一处其余链接
   - 代码注释：中文；关键处必须有注释（非显然意图/不变量/边界/反直觉分支/公共契约）；禁止执行过程叙述、复述代码、变更史；平凡代码不应有注释
   - 存在真实、长期取舍却没有记录 ADR
8. **可观测性与注释完整性**：
   - 关键路径（外部边界、错误/降级/重试、状态转换、启动关闭）缺必要日志 = Important；级别误用（错误/失败路径用 INFO 或更低）= Important。
   - 设计/tasks.md 列出的日志点未落地 = Important。
   - 关键处缺关键注释 = Important。
   - 日志泄露敏感数据、循环刷屏、无信息占位，或引入多余的日志依赖 = Important。
   - 冗余或叙述性注释 = Suggestion。

### 深模块判据

- **深模块** = 小接口 + 大行为；接口和实现一样复杂就是**浅模块**。
- **删除测试**：删掉这个模块，复杂度是消失（pass-through，应删）还是扩散到 N 个调用方（在挣钱，应留）？
- **接口即测试面**：需要绕过接口才能测，说明模块形状不对。
- **一个 adapter 是假 seam，两个才是真 seam**：没有实际变化就不要引入 seam。

### Fowler 坏味道基线（12 条）

仓库文档（AGENTS.md 等）之上，Standards 轴始终携带此基线。三条约束：

- **仓库标准优先。** 文档化的仓库标准永远赢；它认可基线会标记的东西时，压制该坏味道。
- **永远是判断。** 每条是贴了标签的启发式（"可能的依恋情结"），不是硬违规。
- **工具已强制的跳过。**

每条读作 *是什么 → 怎么改*：

- **神秘命名** — 函数、变量、类型名不透露它做什么、存什么。→ 改名；改不出诚实名字，说明设计糊了。
- **重复代码** — 相同逻辑形状出现在多个 hunk 或文件里。→ 提取共享形状，两处调用。
- **依恋情结** — 方法伸手拿别人对象的数据多于自己的。→ 把方法移到它依恋的数据上。
- **数据泥团** — 几个字段或参数总是一起旅行（一个想出生的类型）。→ 捆成一个类型传递。
- **基本类型偏执** — 基本类型或字符串顶替了值得有自己的类型的领域概念。→ 给概念一个小类型。
- **重复 Switch** — 对同一类型的相同 `switch`/`if` 级联反复出现。→ 用多态替换，或一处 map 两处共享。
- **霰弹式修改** — 一个逻辑变更逼你在许多文件散落编辑。→ 把一起变的东西聚到一个模块。
- **发散式变化** — 一个文件或模块为几个不相关的理由被编辑。→ 拆开，让每个模块只为一个理由变化。
- **投机性通用** — 为规格里没有的需求加的抽象、参数、钩子。→ 删掉；内联回去，直到真实需求出现。
- **消息链** — 调用方不该依赖的长链 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法藏起整段行走。
- **中间人** — 一个类或函数大部分只是转发。→ 砍掉，直接调真实目标。
- **拒绝遗赠** — 子类或实现者忽略或覆盖了继承来的大部分。→ 放弃继承，用组合。

## 验证（收尾）

相关命令在本回合运行过且输出已读。审查两轴各自结束时确认。

## 完成前自审

自审由 `finish-change` 收尾门统一执行（逐条对照 specs/tasks，确认完整实现、无遗漏）；本技能只负责审查发现，审查中发现的缺口按 Critical/Important 报告。

## 可选：并行只读子代理

复杂 diff 或"固定点以来 diff"审查（用户说"审查某分支/PR/工作区"）时，按 `subagent-dev` 派发模式派两个**只读**子代理分别跑两轴，互不污染上下文：

1. 固定点：用户说的就是固定点（commit SHA、分支、tag、`HEAD~5`）；没指定就问。diff 命令 `git diff <fixed-point>...HEAD`（三点，与 merge-base 比较）。
2. Spec 源按序找：commit 消息里的 issue 引用 → 用户给的路径 → `docs/changes/<change>/specs/**/spec.md`（lazy flow 默认）→ 都没有就问；用户说没有，Spec 子代理报 "no spec available"。
3. **Spec 子代理简报**："报告 (a) spec 要求但缺失或部分实现的需求；(b) 没被要求的行为（范围蔓延）；(c) 看起来实现了但实现有问题的需求。每条引用 spec 原文。400 词以内。"
4. **Standards 子代理简报**：粘贴本文件的坏味道基线全文 + 仓库标准源路径。"报告 (a) 违反文档化标准的每一处（引用文件+规则）；(b) 发现的基线坏味道（命名+引用 hunk）。区分硬违规与判断。400 词以内。"
5. 聚合：两轴报告分开呈现，不合并不重排。

## 输出

```markdown
## Spec 轴
- Critical: <file:line> <issue>
- Important: <file:line> <issue>

## Standards 轴
- Critical: <file:line> <issue>
- Suggestion: <file:line> <issue>

## Verdict
Passed | Needs changes
```

（每轴各出各的发现，禁止跨轴合并重排。）没有发现时，说明无发现，并提及剩余风险或测试盲区。
