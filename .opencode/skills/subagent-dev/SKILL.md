# 子代理开发

full 变更的实现默认由主控 inline 完成。任务独立且可并行、或需要隔离上下文（大 diff、探索性任务）、或用户明确要求时，使用本技能派发子代理；每个派发任务使用一个全新的实现子代理。

在 OpenCode 中，用 `task` 工具派发子代理，使用可用的子代理类型，如 `general` 做实现/审查、`explore` 做代码库调研。角色由你提供的提示词决定。

## 何时不用

- tiny 或 patch 修改。
- 任务仍需要设计决策、明确路径或验证命令。
- 任务之间会触碰相同文件或行为：不能并行；改为串行派发，或由主控 inline 实现。

## 控制器规则

- 派发时每个任务使用全新子代理；未派发的任务由主控直接实现。
- Lazy Goal 的控制工具只由主控调用。实现子代理不得调用 `lazy_goal_set`、`lazy_goal_progress`、`lazy_goal_mark_done`、`lazy_goal_pause`、`lazy_goal_resume` 或 `lazy_goal_abort`。
- 实现全部完成后进入 review/finish；完整实现自审由收尾门统一执行（见 `finish-change`）。
- 提供完整上下文；子代理不继承你的会话上下文。
- 实现子代理可能触碰相同文件或行为时，必须串行运行。
- 不要相信实现者的成功报告。自己读 diff 并独立验证。
- **界面任务**：子代理返回后，主控必须独立用 `opencode_computer_*` 截取改动后的真实界面并观察确认，不能只信子代理的截图或文字报告。
- 审查子代理只在实现存在后使用，并给它们只读/审查指令，除非明确让它们修复。

## 实现者提示词形状

用 `subagent_type: "general"` 启动 `task` 时使用此结构：

```text
你是由 full Lazy Flow 主控委托的实现子代理。直接完成这一个任务，不要再次派发子代理。

Change: <change id>
Task: <确切的 checkbox 文本>
相关 spec/design:
<粘贴相关 requirements/scenarios/设计决策>

日志点:
<本任务要打的事件 + 级别 + 上下文；确实不适用的写「无日志点：<原因>」；填不出就不要派发>

可能涉及的文件:
<确切路径>

规则:
- 先加载 `using-lazy-flow` 与 `subagent-dev`；你是已委托的实现子代理，直接完成任务而不再派发。
- Lean 模式不是 off 时，先加载 lean-check。
- 行为变更先加载 tdd-cycle，并完成 RED：运行并确认预期失败，再实现 GREEN。
- 界面任务加载 `ui-visual-verify`：用 `opencode_computer_*` 截取改动后的真实界面并观察自检，不符则修正重截；返回截图路径与观察结论。
- 不要调用 Lazy Goal 工具；将验证证据和阻塞完整返回给主控。
- 关键路径按仓库日志规范加日志；关键处加中文注释（见 AGENTS.md 的日志/注释规范）。
- 保持最小正确 diff。
- 不做无关清理。
- 运行: <确切验证命令>

返回:
- 改动的文件
- 运行的命令和结果
- 日志点实现清单（每点对应代码位置）+ 注释关键点
- 界面任务：截图路径与观察结论
- 任何阻塞
```

派发前替换所有尖括号文本。做不到就不要派发。

## 审查循环

实现者返回后：

1. 自己检查改动文件。
2. 运行或重跑聚焦验证命令；界面任务另用 `opencode_computer_screenshot` 独立截图并观察确认。
3. 先审查 spec 符合性：行为精确，无缺失/多余范围。
4. 再审查代码质量：最小、清晰、无投机抽象、错误处理安全、关键日志与注释是否具备。
5. 仍有问题时，优先继续派发聚焦修复任务；主控也可直接修复。
6. 只有独立验证后才勾选 `tasks.md`。

## 可选审查子代理

复杂 full diff 可派发独立的 `general` 只读审查任务：

- Spec 符合性审查：对比 diff 与 proposal/spec/design/task，只报告发现。
- 代码质量审查：检查最小性、复用、错误处理、安全、无障碍，只报告发现。

把审查输出当输入，不当真相。行动前自己验证发现。
