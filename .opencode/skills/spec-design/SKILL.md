# 规格设计

完整变更在动生产代码之前使用；需求卡（停点 1）已获用户确认后，产出**协作卡 + 流程契约**（停点 2）与 spec 产物。

直接在 `docs/changes/<change>/change.md` 和 `docs/changes/<change>/specs/` 下创建和编辑产物文件。

## 入口检查

1. 如果还没分级，先加载 `using-lazy-flow`。
2. 确认这确实是 `full`。如果是 `tiny` 或 `patch`，推荐更轻的路径。
3. 确定 change id：
   - 优先使用命令参数。
   - 否则从请求的变更推导一个简短的 kebab-case id。
   - 如果有多种合理解释，问一次。
4. 检查 `docs/changes/<change>/` 是否已存在。
   - 已存在则先读已有产物再更新，不要盲目覆盖。
   - 如果属于不同意图，停下来问。
5. 读 `docs/changes/<change>/change.md` 的 `## 需求卡` 段（grill-me 落盘）和仓库根 `CONTEXT.md`（术语表，如有）；产物使用其中的术语，并保留需求卡段。
6. 确认需求卡已经用户明确确认（停点 1）；上下文里看不到确认或修改记录时，先呈现需求卡并等待，不进入设计。

## 流程

1. 探索相关代码、测试、已有 `docs/specs/`、`CONTEXT.md` 和项目约定。
2. 仅当歧义会改变范围、行为或风险时才问澄清问题。
3. 存在真实设计取舍时对比方案，推荐最省力的安全方案。
4. 在 `change.md` 中创建或更新 `## 协作卡（类图形）`、`## 流程契约`、`## UI 草图`（仅界面变更）、`## 影响`；创建或更新 `specs/<capability>/spec.md` 和 `state.json`。
5. 停下前自查产物。
6. **只呈现协作卡 + 流程契约（界面变更另加 UI 草图）+ 至多 3 个取舍/问题，停下等用户确认（停点 2）**；用户确认或修改后才建议 `/plan`。未确认前不规划、不实现。

## 禁止占位符

最终产物不得包含未解决的占位符，如 `<title>`、`<path>`、`<behavior>`、`TODO`、`TBD`、`lorem` 或示例文本。信息未知但重要时，问用户，或在 `## 影响` 里写成显式开放问题。

## change.md

`docs/changes/<change>/change.md` 是唯一变更说明，章节固定：需求卡（保留不覆盖，grill-me 落盘）+ 协作卡 + 流程契约 + UI 草图（仅界面变更）+ 影响。全文 ≤ 3 屏。

### 协作卡（类图形）

```markdown
## 协作卡（类图形）
边界：<进程/服务划分>
图例：[增]=新增　[改]=修改　[有]=既有复用（不动）　──▶=调用方向

[改] <入口/既有模块> ──<接口>──▶ [增] <新组件>
[增] <新组件> ──<接口>──▶ [有] <既有模块> ──HTTP──▶ [有] <后端接口>

共享接口：<中文签名（入参、返回）>（<谁的唯一公共入口>）
改动边界：新增＝<…>；修改＝<…>；复用不动＝<…>
不变量：<…>
禁止形状：<…>
偏离定义：<…>
```

规则：

- **中文为主、英文为锚**：组件与关键动作用中文名，英文代码标识只在本卡配对一次（如：导出编排（exportFlow）：启动（start））；流程契约全中文引用。
- 节点标记 `[增]`/`[改]`/`[有]` 齐全；只画跨模块/跨进程接线，边标用到的接口名，跨进程标协议与路径。
- 共享接口写清"唯一公共入口"+ 中文签名（入参、返回）；完整函数签名以本行为准，流程契约只引用关键参数。
- 改动边界一行说清新增、修改、复用不动的模块；`[有]` 节点视为不许改。
- 卡尾必须有不变量、禁止形状、偏离定义三条。
- 确无结构影响时，本段写一句「无结构影响：<原因>」。
- ≤ 一屏。

### 流程契约

```markdown
## 流程契约
触发：<什么事件/操作>（多入口时注明等价）
主链：
入口参数（多入口时必写）：<两入口同型的关键入参>
入口A ─┐
入口B ─┴→ 节点 → 节点 → …
        → …（括号只装参数/条件/说明；跨进程就地标：取数（前端→后端：GET /api/…））
返回：成功 = <…>；失败 = 枚举原因（<…>），入口统一展示
异常线：
- <链路位置> → <处理 + 日志级别>，是否产文件
```

规则：

- 主链是一条流水线：入口分叉（`─┐`/`─┴`）汇入，`节点 → 节点` 一路到底；不编号、不缩进分层、不分块。
- 括号只装参数/条件/说明，节点保持干净。
- 多入口/多调用方必须写入口参数行并声明"同型"。
- 跨进程就地标（协议 + 方法 + 路径）。
- 异常线按链路位置挂钩（不按编号），每条写清处理、日志级别、是否产文件。
- 只写关键参数；完整签名放协作卡的共享接口行。
- ≤ 一屏。

## specs/<capability>/spec.md

规格文件只定义可观察行为。它们是行为契约，不是实现计划。

从需求卡编号 1:1 派生：每条验收标准对应 requirement/scenario（正式化，不重写、不新增内容）。每条 requirement 正文 ≤ 2 句；每个 scenario 一行。

每个 capability 一个 delta spec：

```text
docs/changes/<change>/specs/<capability>/spec.md
```

允许的章节：

```markdown
## ADDED Requirements
## MODIFIED Requirements
## REMOVED Requirements
## RENAMED Requirements
```

规则：

- 每个生效 requirement 使用 `### Requirement: 名称`。
- 每个生效 requirement 至少有一个 `#### Scenario: 名称`。
- Scenario 标题必须恰好四个井号。
- 规范性行为用 SHALL/MUST。
- `ADDED` 用于新行为。
- `MODIFIED` 必须包含从 `### Requirement:` 到所有 scenario 的完整更新块。
- `REMOVED` 必须包含 `**Reason**:` 和 `**Migration**:`。
- `RENAMED` 使用 `FROM:` 和 `TO:`，仅用于改名。
- 改名后的行为变更放在 `MODIFIED`，使用新名字。
- 不要提及内部类/函数名、库选型或逐行实现。

对修改的 capability，先读当前主 spec 并复制原 requirement 块再编辑。不要写不完整的 modified 块。

不要凭空发明 capability。列修改的 capability 前先检查 `docs/specs/`。

## UI 草图

界面变更时，`change.md` **必须**包含 `## UI 草图` 段：用文字给出布局、区块、组件与交互要点。界面变更**必须至少落一份可视设计稿**：简单界面用该文字草图；复杂界面若用户确认 `designDemo=true`，以 `design-demo.html` 为主设计稿，`## UI 草图` 至少保留要点与指向 demo 的说明。

## design-demo.html

当本变更是**复杂界面**变更且用户确认 `designDemo=true` 时，产出 `docs/changes/<change>/design-demo.html`：

- 单文件：HTML + 内联 CSS + 内联 JS，无外部依赖、无框架、无构建。
- 带示例数据，展示设计效果与基本交互（点击/切换/状态变化等），供用户做基本功能验收。
- 不追求生产级实现，只表达设计意图；范围保持最小。

简单界面不产出 HTML，用 `change.md` 的 `## UI 草图` 即可。

## 影响

```markdown
## 影响
- 能力：新增 <capability>；修改 <capability>（与 specs 文件一致）
- Data：迁移/存储变更，或 none
- Risks：具体风险 2–3 行，或 low
```

## state.json

字段与转换以 `using-lazy-flow` 的「状态」为唯一出处。本阶段创建/更新：

- change 的 `state.json`：`level = "full"`、`phase = "design"`、`grilled = true`。
- 界面变更：记录用户明确确认的 `visualVerify`/`visualReport`/`designDemo`（未确认按 `false`）。
- 全局 `.opencode/lazy/state.json`：`activeChange`、`level = "full"`、`phase = "design"`。
- 确认停点为软门，不新增状态字段。

## 自查门

停下前检查：

- 无未解决占位符。
- 需求卡每条验收标准在 spec 里有对应的 requirement/scenario（编号可追溯）。
- 协作卡：节点标记齐全、`[增]`/`[改]`/`[有]` 与实际意图一致；共享接口有中文签名；改动边界一行；不变量/禁止形状/偏离定义三条齐；≤ 一屏。
- 流程契约：入口参数行（多入口时）已写；主链完整；异常线覆盖关键失败与日志级别；≤ 一屏。
- `## 影响` 的能力列表与 specs 文件一致；Data/Risks 已写。
- 术语与 `CONTEXT.md` 一致；引入的新领域概念已回写 `CONTEXT.md`。
- 界面变更：`## UI 草图` 已写；三开关已记录。
- **冲突检查**：把需求卡/协作卡/spec 与 `CONTEXT.md`、`AGENTS.md`、`docs/adr/`、代码规范、架构规范、测试规范对照；发现冲突先列出并解决，解决不了就停下来问用户。带着冲突不进入规划、不写代码。
