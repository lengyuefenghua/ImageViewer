## Workflow
- **语言**：始终使用中文思考和回复。
- 任何开发请求先通过 skill 工具加载 `using-lazy-flow` 分级并按其路由；技能已注册，不需要文件搜索。
- **行为基线**：动手前先明示假设、有歧义先问、有更简单方案就反驳；只写解决问题的最小代码；只改必须改的（不动相邻代码/格式，无关死代码只提不删，清理自己的孤儿）；把任务转成可验证标准、凭新鲜证据循环到通过。细节分别以 `lean-check`、`execute-change`/`review-change`、`tdd-cycle` 为准。
- 分级：`tiny` 最小修改（文案/样式/小修复/局部优化，不改契约；重要代码必须聚焦验证；不审查；三行记录到 `docs/changes/tiny-log.md`）；`patch` 单功能/子系统行为变更 + 轻量审查；`full` 仅限共享契约/架构级重组/数据迁移/高不确定性 + 三轴审查（行为/契约/标准）。
- full：先统一术语（`CONTEXT.md`），需求卡落盘 `change.md`（停点 1 确认）；再产出协作卡与流程契约（停点 2 确认），然后才规划。
- **确认面最小化**：要用户确认时只呈现一屏关键决策（需求卡／协作卡＋流程契约），其余给路径；变更文档守预算（卡各 ≤ 一屏，禁止复述与铺垫）。
- 各纪律的判定以对应技能为唯一出处（测试 → `tdd-cycle`，视觉 → `ui-visual-verify`，收尾/状态 → `finish-change`、`using-lazy-flow`），本文件只留摘要。
- **界面设计必出可视设计稿**：文字 UI 草图是底线，复杂界面可升级为单文件 HTML demo；tiny 纯样式微调豁免。
- **执行中新需求/范围变更**（含 `/apply`、build agent）：先出方案并获用户明确确认再改代码，禁止直接改；仅当用户明确声明本变更期间不再逐次确认（change 状态 `confirmWaived=true`）才可连续实施；该豁免不覆盖提交/推送门与 `lazy_computer_*` 权限门。
- 测试默认不写：只对命中 `tdd-cycle` 漏测后果闸的行为写测试并走 RED-GREEN；不做文字断言。
- full/patch 完成前由收尾门自审（逐条对照需求卡验收标准、协作卡、流程契约与 specs/tasks）；full 变更不自动续跑，`tasks.md` 未完成就继续。
- **权限门**：未经用户明确许可，不得调用 `lazy_computer_*`（视觉验证）；**人工验收通过前禁止提交**；`git commit` 与 `git push` 都必须获得用户明确许可（commit 许可不等于 push 许可）。
- `/goal <最终目标>` 在已确认范围内提供一次性实施授权，持续推进并在阻塞时暂停；不得绕过上述权限门。
- full 实现默认 inline；任务可并行或需隔离上下文时按 `subagent-dev` 派发，主控负责验证、审查和收尾。
- 声明 done/fixed/passing 之前，在当前回合运行相关验证命令并读取输出；只跑最小相关命令，禁止惯性全量。
- 只有存在真实且长期值得记录的取舍时才写 `docs/adr/` 决策记录。

## 代码注释
- 注释用中文。
- 默认不写；但关键处**必须**有注释：非显然的为什么/权衡、不变量、边界条件、平台或库怪癖、反直觉分支、公共 API 契约。关键处缺失注释视为缺陷。
- 只写意图、约束、边界或为什么（如平台限制、反直觉处理、安全考量），不复述代码。
- 禁止执行过程叙述（“先…再…”“这里我们…”）、复述代码、变更史。
- 名字能表达的、平凡代码（getter、显然的赋值/循环）不加注释。

## 日志
- **日志是行为变更的交付物**：所有行为变更必须评估并列出日志点（事件 + 级别 + 上下文）；涉及外部边界 / 异常降级重试 / 状态转换 / 用户可见结果的必须落地，确实不适用的写明原因。用级别控制输出内容；缺日志视为未完成。
- **豁免**：很小的一次性验证/临时项目（spike、一次性脚本、临时 demo）按项目整体豁免，需一句话说明。
- 优先使用仓库已有的 logger；不要为此引入新依赖。
- 日志文案用中文。
- 日志格式固定为 **时间 等级 模块 源 内容**：时间＝仓库现有时间格式（无则 ISO 8601）；模块＝所属模块/子系统；源＝代码位置（`文件:行` 或函数名）；内容＝事件描述。
- 示例：

  ```text
  2026-10-15 14:30:00 INFO  订单模块 order.js:88 订单创建成功（订单 #1234）
  2026-10-15 14:31:02 ERROR 支付模块 pay.js:42 支付失败：网关超时（订单 #1234）
  ```
- 级别从低到高：
  - TRACE：最细粒度跟踪（框架内部流程、逐行调试），生产一般关闭。
  - DEBUG：调试信息（变量值、分支走向），开发/排障时使用。
  - INFO：正常运行信息（启动、配置加载、关键业务节点）。
  - WARN：警告（潜在问题、重试、降级、容量接近阈值）。
  - ERROR：错误（当前操作失败，通常需要关注或告警）。
  - FATAL：致命错误（服务/进程无法继续运行）。
- 必须记录的点：外部边界（I/O、网络、DB、文件、子进程）的调用与失败；异常/降级/重试/回退路径及原因；关键状态转换（开始/结束、状态机迁移）；启动与关闭。
- 每条日志带定位上下文（实体/请求/任务标识 + 动作 + 结果）。
- 禁止：密钥/token/密码/PII 等敏感数据；循环内逐条刷屏；无信息占位日志；把日志当注释复述代码。

## 文档层级
- 每个事实只有一个家：决策 → `docs/adr/`；行为契约 → `docs/specs/`；术语 → `CONTEXT.md`；需求卡／协作卡／流程契约 → `docs/changes/<change>/change.md`；变更过程 → `docs/changes/`；tiny 记录 → `docs/changes/tiny-log.md`；常设规则 → 本文件。
- 别处引用用相对路径链接，不粘贴副本。
- 写当前状态，不写变更史（"之前/现在"这类叙事只允许在 ADR 和归档中）。

## Gotchas
- 只保留仓库特有的陷阱、前置条件、昂贵测试套件、环境怪癖，或 agent 很可能忽略的约定。
