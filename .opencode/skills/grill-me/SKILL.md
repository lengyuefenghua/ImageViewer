# 拷问设计

只澄清会改变范围、行为、风险、数据、权限或验收方式的未知项。需求已经明确时，快速给出 `Passed`，不要为走流程制造问题。

## 第 0 步：术语先行

澄清需求和边界之前，先提取需求中的核心术语，逐一确认其定义、范围以及容易产生歧义的地方。术语统一之前不进入下一步。

- 发现含糊、重载或前后不一致的用词时，提出规范术语，用边界场景拷问，直到用户确认。
- 术语一确定就写入 `CONTEXT.md`（仓库根，惰性创建），只记术语、不记实现。
- 每条格式：

```markdown
## <术语>
一句话定义。Avoid: <应避免的别名>
```

## 假设与反驳

- 动手前先明示你依赖的假设；不确定就停下来问，不静默猜测。
- 需求存在多种合理解释时全部列出让用户选，不独自选一种继续。
- 存在更简单或更省的方案时主动指出并反驳当前方案，不照单执行。
- 有不清楚的地方就停下，点明哪里不清楚并提问。

## 提问方式

1. 先自行检查当前项目中的相关代码、测试、项目指令、`CONTEXT.md` 和已有规格；不要让用户回答可由项目文件确认的事实。
2. 每个问题给 2–3 个具体选项并标注推荐项，让用户选择或补充，不必从零描述。
3. 一轮优先问完相互独立的问题；仅在本轮答案会影响后续问题时等待下一轮。
4. **已被前置规则排除、不可能出现的边界，不再换方式重复提问。**
5. 用户确认共识，或不存在影响实现的未知项后结束。

## 拷问维度

围绕以下维度逐一排查，有疑问就追问：

1. **业务**：业务目标、使用场景、业务流程、业务规则、异常情况、功能边界。
2. **范围和行为**：正常路径、错误路径、边界和空状态是否影响实现？
3. **结构**：入口/调用方有哪些？期望它们共享什么、独有什么？有没有现成模块/接口可复用？改动预期落在哪些模块？
4. **风险**：数据、权限、安全、迁移、回滚或无障碍是否需要决策？
5. **YAGNI**：是否存在只为未来预留的字段、API、开关或抽象？
6. **验收**：每个场景是否有可执行的验证方式？关键失败场景期望用户看到什么行为？

## 结束条件

每轮结束重检三项：

1. 是否还有核心业务需求未明确？
2. 是否还有关键边界或异常情况未确认？
3. 是否存在相互矛盾的描述？

三项都无则结束提问；仍有未知项则继续下一轮。不设问题数量目标，未知项清空即结束。

## 需求卡

确认结论组织成需求卡（写入 `change.md` 的 `## 需求卡` 段）：

```markdown
## 需求卡
目标：<一句话>
验收标准：
1. <正常场景>
2. <边界场景>
3. <关键失败场景>：期望 <用户可见表现>
非目标：<本次不做>
```

- 业务语言：不出现 SHALL/MUST、类名或函数名；每条验收标准必须可验证。
- 关键失败场景必须有期望的用户可见表现。
- 超过 7 条说明范围没收敛 → 建议拆变更，而不是继续加条。
- 全文 ≤ 一屏。

## 落盘

每轮结束时把本轮确认结论**批量**写入 `docs/changes/<change>/change.md` 的 `## 需求卡` 段（该文件此时可能只有此段，协作卡与流程契约由 `spec-design` 后续补齐），不要依赖上下文压缩后的记忆。

- change id 由 `/start` 给定；未给定则先推导一个 kebab-case id 并创建 `docs/changes/<change>/`。
- 确认的术语同时写入 `CONTEXT.md`。
- 需求卡随 `change.md` 一起归档。

## 界面变更

若变更涉及视觉界面（前端页面/组件、样式、布局、响应式、窗口/对话框、自绘/画布）：

1. **必须给出可视设计稿**：**文字 UI 草图**（布局/区块/组件/交互要点）是底线，任何界面设计都不得只给文字描述而无草图，让用户在澄清阶段看到设计方向（最终由 `spec-design` 落盘到 `change.md` 的 `## UI 草图` 段）。
2. 界面复杂时（由你判断），问**是否升级为单文件 HTML 设计效果 demo**？→ `designDemo`。
   - `true` → 产出 `design-demo.html` 作为主设计稿。
   - `false`（或简单界面）→ 以第 1 步的文字 UI 草图为准，**也必须给草图**。
3. 问用户：**是否使用视觉测试与验证（`lazy_computer_*`）？** → `visualVerify`。
   - `true` 时再问**是否需要视觉验收报告** → `visualReport`。
   - `false` 时本变更**不得使用** `lazy_computer_*`。
4. 视觉开关（`visualVerify`/`visualReport`/`designDemo`）必须来自用户明确确认（默认 `false`，未许可禁止调用 `lazy_computer_*`）；结论先记入全局 `.opencode/lazy/state.json`，change 建立后由 `spec-design` 同步进 change 的 `state.json`。

## 产物审查（存在 change.md 时）

审查 active change 的产物文件：

- `change.md`（需求卡；协作卡与流程契约如已存在）

## 结论

按严重程度列出发现：

- Critical：规划前必须修复。
- Important：规划前应当修复。
- Suggestion：可选的简化或澄清。

最后只给一个结论：

- `Passed`
- `Needs changes`
- `Redesign required`

结束提问且重检通过时，**只呈现需求卡 + 至多 3 个取舍/问题，停下等用户确认（停点 1）**；用户确认或修改后才进入设计（`spec-design`），未确认前不得进入设计或规划。

没有 active change 时只输出澄清结论，不写状态文件。用户确认需求卡后，若 full change 的产物已存在，更新全局和 change 的 `state.json` 为 `phase = "design"`、`grilled = true`。
